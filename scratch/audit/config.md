# config

## SUMMARY
Config-truth and recompute analysis of the live World Cup pool. matchPoints is a pure derived cache off the CURRENT league row (rules + multipliers), with no rule-versioning and no audit trail anywhere in the schema. The dominant fairness landmine: a mid-tournament edit to scoringRules / roundMultipliers / boosterMultiplier triggers recomputeLeague, which IMMEDIATELY and RETROACTIVELY rescores every already-finished match (incl. today's Mexico opener) under the new rules. The live Railway league was seeded with pure schema defaults (seed.mjs sets only name/slug/token/admin); that means buyInCents=0 (pot displays $0), autoUnderdogEnabled=0 (the +5 underdog bonus is NEVER auto-flagged and only exists if the admin manually flags matches), autoSyncEnabled=1, roundMultipliers all 1 (the final is worth the same as a group game). Several admin levers are unguarded and the admin is also a player: enterResult has no kickoff guard (entering a result early locks everyone's picks), setUnderdog has no time guard (admin can add/remove a +5 on a finished match, recompute is immediate), results are silently editable, and removeMember hard-deletes a rival's entries/picks/points. No admin action (result entry/edit, rule change, member removal, underdog flag) records who did it or when. Results authority is correctly scoped to the PRIMARY (lowest-id, seeded) league so players cannot mint a throwaway league to gain results power.

## RISKS
- [high/high] Mid-tournament scoring-rule change is retroactive: rescopes already-played matches immediately
  evidence: src/lib/services/leagues.ts:400-426,442-464; src/lib/services/results.ts:316-319,389-404
  updateLeagueSettings detects any change to scoringRules, boosterMultiplier, or roundMultipliers (scoringChanged) and, in the same transaction, calls recomputeLeague which re-scores EVERY finished match for the league using the new rule values. matchPoints carries no rule-version, so there is no concept of 'the rules as of when this match was played.' Today's matchday-1 result (Mexico opener) and all future-finished matches would silently change scores the instant the admin saves a new exact/outcome/scorer/firstTeam/underdog value, a new booster multiplier, or new per-round multipliers. The admin is also a player: after seeing which way matchday 1 fell, they could tune (e.g.) scorer from 8->12 or final-multiplier up to favor their own pick profile, and the standings rewrite happens with no warning and no audit record. For a $600 pot this is the single highest-impact fairness lever.
- [high/high] No audit trail for any admin action (result entry/edit, rule change, member removal, underdog flag)
  evidence: src/db/schema.ts:117-152,18-41; src/lib/services/results.ts:90-134; src/lib/services/leagues.ts:400-426,483-498
  The schema has no audit/history table. Result rows record resultSource ('manual'/'auto') but not who entered/edited them or when (no updatedAt on match result fields). leagues has only createdAt — a scoringRules/payoutSplit edit overwrites the prior JSON with zero trace. removeMember hard-deletes a member's entries/picks/boosters/matchPoints. Combined with the editable-results and retroactive-rule mechanics above, an admin-player can alter a finished score, change the scoring formula, flip an underdog on a completed match, or delete a rival, and there is no forensic record any of it happened. In a real-money friend pool this removes all accountability and makes disputes unresolvable.
- [high/high] Manual setUnderdog has no time guard — admin can add/remove a +5 bonus on a finished match
  evidence: src/lib/services/results.ts:269-295; src/app/api/matches/underdog/route.ts:7-23; src/db/schema.ts:40
  setUnderdog only validates that underdogTeamId is one of the match's two teams; there is no check that kickoff has passed or that the match is unfinished. If the match is already finished it recomputes immediately. Because the live league has autoUnderdogEnabled=0, the underdog flag is purely a manual admin act. An admin-player can therefore designate (or remove) the underdog on a match AFTER picks lock and AFTER the result is known, directly granting or denying the +5 (x round x booster) bonus to whoever predicted that side — swinging standings with full knowledge of outcomes and no audit trail. The auto path is safe (frozen at kickoff); the manual path is the exposure.
- [medium/high] enterResult has no kickoff guard — entering a result early force-locks and exposes everyone's picks
  evidence: src/lib/services/results.ts:136-141,90-134; src/lib/services/picks.ts:52-54,98-101
  enterResult validates only score ranges; nothing prevents finishing a match before kickoff. picks.ts treats status==='finished' as a pick lock and reveals others' picks at kickoff/finish. An admin-player could enter a (provisional or bogus) result on an upcoming match to freeze all opponents' predictions prematurely, or to expose hidden picks, then clearResult to revert — leaving status back to scheduled but having already snapshotted/locked at a chosen moment. Results are also freely re-enterable (overwrite) with no confirmation or diff.
- [medium/high] removeMember hard-deletes a competitor's entire footprint with no recovery or record
  evidence: src/lib/services/leagues.ts:471-498
  A league admin can remove any member except themselves; the operation deletes that user's matchPoints, boosters, picks, and entries inside one transaction. There is no soft-delete, no archive, and no log. An admin-player in a tight race could delete a leading rival; the rival simply vanishes from the leaderboard with no trace they ever played. Recovery requires a DB backup.
- [medium/high] Live league economic config is unset/defaulted: buyInCents=0 (pot shows $0) and payoutSplit editable mid-tournament
  evidence: scripts/seed.mjs:110-118; src/db/schema.ts:24,27; src/lib/services/leagues.ts:382-399,557-569
  seed.mjs never sets buyInCents, so the live league stores 0; prizePool() = buyInCents * entryCount renders the in-app pot as $0 while ~$600 is collected off-app, so the app cannot be the source of truth for who is owed what. Separately, payoutSplit and buyInCents are editable at any time via settings with no lock and no audit, so the admin could change the 60/30/10 split after standings are known. Low technical severity but directly money-relevant for payout fairness.
- [low/high] Default roundMultipliers leave the final worth the same as a group game; raising them mid-tournament is retroactive on finished knockouts
  evidence: src/db/schema.ts:32-36; drizzle/0000_fat_stone_men.sql:36; src/lib/services/leagues.ts:419-426,442-464
  The seeded roundMultipliers are all 1 including the final, so a correct final prediction scores identically to a group match — a design/fairness choice players may not expect. More importantly, if the admin later raises knockout multipliers, recomputeLeague retroactively rescopes any already-finished knockout matches under the new multiplier (same retroactive mechanism as the rules-change risk), with no audit record.

- (recompute-rules-source) recomputeMatchForLeague reads scoringRules, roundMultipliers and boosterMultiplier FRESH from the league row on every recompute and re-derives breakdown.   [src/lib/services/results.ts:316-369]
