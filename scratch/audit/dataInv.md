# dataInv

## SUMMARY
Data inventory for a Monte Carlo simulator over fabiansredcard. Static data: data/fixtures.json (104 fixtures: 72 group + 16 r32 + 8 r16 + 4 qf + 2 sf + 1 third + 1 final; all 32 knockout fixtures n=73..104 have null team codes with text placeholder labels), data/teams.json (48 teams {name,code,group}), data/rosters.json (48 squads keyed by FIFA code, 1246 players {name,position}). Matchday is NOT derived in calendar.ts — it is precomputed at seed time as the America/New_York calendar date of kickoff_utc (seed.mjs); 34 matchdays total 2026-06-11..2026-07-19, 33 remain after today. ESPN feeds are key-less: scoreboard (1X2 DraftKings odds, ET-grouped ?dates=YYYYMMDD == matchday column), core-API propBets pages for First Goalscorer (provider 100, limit=100, ~12 pages/event), and seasons/2026/athletes/{id} for name resolution; ESPN event ids are never persisted — matching is by normalized kickoff instant + home-team abbreviation, and matches.id IS the FIFA match number 1..104. DB is better-sqlite3 at DB_PATH (default .data/app.db, gitignored, auto-migrated on open). CRITICAL CAVEAT for "real data": the local .data/app.db is a near-empty dev instance (0 picks, 0 finished matches, 0 players, 0 odds, 1 user) — the live pool's picks/results live on the deployed host, so the simulator needs a production backup (.data/backups/ shows the format) or must fetch odds/results itself. MatchOdds round-trips verbatim as JSON in matches.odds_json (confirmed sample), scorer odds land as one row per (match_id, player_name) in scorer_odds, wholesale-replaced per refresh. FAKE_NOW pins the game clock; vitest only collects tests/**/*.test.ts and playwright only e2e/, so scratch/<label>/ files are never picked up by npm test.

## RISKS
- [medium/high] No real pool data exists locally — simulator 'real data' requires a production export
  evidence: sqlite3 -readonly .data/app.db counts; src/db/index.ts:15; src/instrumentation.ts:40-47,75
  The local .data/app.db has 0 picks, 0 boosters, 0 finished matches and 1 user even though matchday 1 is complete; the live ~$600 pool's picks/results/odds live only on the deployed host. A Monte Carlo run promising 'REAL data' must ingest a production backup (format: .data/backups/app-<ISO>.db, produced daily by src/lib/backup.ts via the hourly scheduler) or fetch odds/results live from ESPN. Running against the local db would silently simulate an empty league and produce worthless fairness conclusions.
- [low/high] Players table empty in local dev DB — scorer-name universe must come from rosters.json
  evidence: sqlite3 -readonly .data/app.db (players=0); scripts/seed.mjs:40-58; data/rosters.json
  Local app.db has 0 rows in players (seed evidently ran before rosters.json landed and was not re-run), so any local scorer-pick simulation joining the players table gets an empty universe. data/rosters.json (1246 ESPN-spelled names) is the canonical source and is what scoring.ts suffix-token matching is calibrated for; the simulator should load it directly. Worth confirming the production host re-ran seed after rosters.json was added, otherwise the live scorer dropdown is empty too — that would suppress scorer picks (8 pts each) for everyone equally but distort expected scoring.
- [medium/medium] ESPN mapping breaks silently if FIFA moves a kickoff
  evidence: src/lib/sync/espn-map.ts:171-172; src/lib/sync/espn-props.ts:91-101
  Event-to-fixture matching requires the normalized kickoff instant to equal matches.kickoff_utc exactly; a rescheduled match is deliberately skipped ('kickoff moved — admin handles') so odds, live scores AND final results stop flowing for it until an admin intervenes. With ~100 matches left, one unnoticed reschedule means picks settle late or not at all — anyone watching could exploit the stale window, and a simulator fetching standalone with the same join will silently drop the same matches. Mitigation for the sim: match by event home/away codes within the matchday, fall back to kickoff only for disambiguation.
- [medium/high] Round multipliers all 1 (including the final) compress late-tournament stakes
  evidence: sqlite3 -readonly .data/app.db leagues row; src/db/schema.ts (roundMultipliers default); jq stage counts on data/fixtures.json
  Confirmed in the league row: round_multipliers = {group:1,r32:1,r16:1,qf:1,sf:1,third:1,final:1}. 72 of 104 matches are group games, so the title is statistically decided by group-stage volume; a player mathematically eliminated before the final can occur. Not a bug — a configuration choice the Monte Carlo should quantify (e.g. P(leader after groups wins pot)) so the group can decide deliberately while changes are still fair (multipliers apply to future matches only).
- [low/high] seed-demo pick model is biased — do not reuse uncalibrated as the behavior model
  evidence: scripts/seed-demo.mjs:144-173
  The only existing pick-behavior model (scripts/seed-demo.mjs:147-158) draws scores uniform 0-2, never picks an away-team scorer, and flips a fair coin for first-team regardless of odds. If imported into the Monte Carlo as the opponent model it will understate scorer points (8 each) and misprice underdog/exact distributions, skewing fairness conclusions about tiebreaks and booster value. Use it only as scaffolding; calibrate pick distributions to the real picks from the production export.
- [low/high] Auto-migration on open can mutate snapshot databases
  evidence: src/db/index.ts:14-27; sqlite3 demo.db 'no such column: odds_json' error
  getDb() unconditionally runs migrations against whatever DB_PATH points to (src/db/index.ts:24). demo.db is already one migration behind (no odds_json column). A simulator that imports src code paths touching getDb() while DB_PATH points at a production backup will ALTER the backup in place — violating the audit's no-modification posture. Always copy backups into scratch/ or open with sqlite3 -readonly for inspection.
