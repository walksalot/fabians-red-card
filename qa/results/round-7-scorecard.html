The one Critical

The winner screen pays out a pot nobody agreed to

The payout reads the live setup draft instead of a snapshot taken when the game started. So if someone opens “New game”, fiddles with the buy-in, and backs out without starting — then resumes the game already in progress — the win screen settles up using the abandoned draft.

Verified in reverse too: a real agreed $2/head to @realaunt became “$12 · send it to @some-other-cousin” — a scannable Venmo QR, for the wrong amount, to someone who was never in the game.

The skeptic attacked this on four axes and it survived all of them, including the strongest defence: the app's own saved stake said enabled:false at the moment the screen displayed $40. Root cause is named in shipped code — payoutFor() in ui.js reads view.setup.buyin rather than a per-game snapshot.

Why it rates Critical: the rubric calls wrong money math S1 outright, and this lands on the exact screen the room uses to settle up.

S3
Status line says 'Playing the preview.' over a paused, silent player when the vinyl is tapped while fast-flow autoplay is still buffering
repro & verdict

Expected The tap is a pause toggle, so the status should read 'Paused — tap play to continue.' (the copy the app itself writes for a deliberate pause), or playback should continue — either way the UI matches the audio.

Actual The pending play() promise from the autostart is rejected by the user's own pause (AbortError), wasInterrupted() maps that to success, and toggleAudio's success branch stamps 'Playing the preview.' after the pause branch already wrote the honest copy — leaving a paused, silent player captioned as playing until the next tap.

  1. Open https://music-timeline-walksalots-projects.vercel.app/index.html?debug=1&seed=707 with network throttled (~400kbps / 400ms RTT; also seen organically at full speed)
  2. New game, Skip photo on every row, Shuffle & start (defaults: classic mode, fast flow on)
  3. On the pass screen tap #btn-pass-continue — fast flow starts loading/playing the song from this tap
  4. Within ~1s, before any audio is audible, tap the big vinyl (#btn-play-song)
  5. Watch the status line: audio stays paused at 0:00 with the play triangle and frozen countdown ring while the status reads 'Playing the preview.' for 6+ seconds; one more tap recovers

S4
Setup edits made in the last ~500ms before a reload are silently lost — draft save is debounced with no pagehide/visibilitychange flush
repro & verdict

Expected The whole half-edited form comes back — the code's own comment says 'everything set on this screen persists'.

Actual saveSetupDraft() fires only on a 500ms debounce timer and nothing flushes it on pagehide/beforeunload/visibilitychange (confirmed by grep of ui.js), so any edit inside the debounce window is lost on an immediate reload or tab eviction.

  1. Open https://music-timeline-walksalots-projects.vercel.app/index.html fresh (clear site data), tap New game
  2. Type a player name, set 'First to' down to 5, toggle the $2 buy-in on, type a Venmo handle
  3. Within half a second of the last edit, reload the page (pull-to-refresh, or an app-switch that discards the tab)
  4. Tap New game again: names come back but target reverts 5→10, buy-in reverts to off, the handle is blank; identical edits followed by a 700ms wait before reload restore everything
